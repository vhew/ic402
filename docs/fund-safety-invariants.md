# ic402 Fund-Safety Invariant Catalog

> **Provenance & how to read this.** Generated by a multi-agent sweep (v2.6.0): Fable drafted ~180
> invariants across five subsystems; an independent Opus agent adversarially verified each; 176 were
> verified (4 hit a tooling retry cap — a known coverage gap, see §4). The maintainer then
> spot-verified the HIGH gaps against source.
>
> **Severity here is "impact IF violated," not reachability.** Read §3 with that lens:
> - **G1, G4** are *known, documented* operator residuals (recoverEscrow-after-GC; shared-pool
>   solvency) — not new.
> - **G2, G3** are *footguns not reachable via the reference stack*: G2's mislabeled EVM buyer needs
>   a non-reference caller (the shipped client sends only ICP sigs to `submitServiceRequest`; EVM
>   marketplace payments use the HTTP path, which is correct); G3's unsafe helper has no in-repo caller.
> - The genuinely-actionable *new* findings are **G5/G6** (an ambiguously-broadcast inbound EVM
>   deposit loses its recovery hash → stranding, no double-pay).
>
> No new *reachable* fund-theft or double-pay was found: the core guards (nonce single-use,
> lock-exclusion, expiry, receipt-only-on-`#confirmed`) verified fully enforced across both rails.

## 1. Introduction

### What a fund-safety invariant is here

A **fund-safety invariant** is a property that, if violated, causes one of:
double-pay, fund loss / stranding, over-spend past a cap, pool insolvency, or an
auth bypass. Each invariant is a *contract* over a specific code path: it names
the guarantee, the rail (`ICP` / `EVM` / `both`), and the exact enforcement site
(`file:line`).

Scope of the audited surface:
- **Published library** — `src/ic402/**` (Gateway, Nonce, Sessions, Escrow,
  EvmEscrow, EvmSender, EvmSigner, Eip712, EvmVerify, Policy, ServiceRegistry, …).
- **Reference wiring** — `example/main.mo` (how a consumer canister composes the
  library; where controller-gating and the `?amount` / null decisions live).
- **Spend caps** — the TypeScript client (`packages/client/**`) and the MCP
  server (`integrations/mcp/**`).

### Method

1. **Draft (Fable).** For each fund-relevant code path, a proposed invariant was
   drafted with its statement, rail, category, and a *claimed* enforcement site.
2. **Adversarial verification (Opus).** Each claim was checked against the real
   code — reading the cited lines, hunting for unhandled variants, ordering gaps
   (fund-move-before-check), force/recovery/GC/upgrade bypasses, and rail
   confusion. Every verdict returns `enforced ∈ {fully, partially}`, the residual
   severity, and — where enforcement is incomplete — a concrete violation path
   with `file:line` citations.

STATUS legend used below:
- **enforced** — verified fully enforced; no violation path found.
- **partial** — enforced on the cited primary path but with a concrete residual
  gap (see §3). Never treat a partial as safe.
- **VIOLATED** — invariant does not hold as stated (none in this pass; all
  incomplete invariants are *partial* — enforced somewhere but with a real gap).
- **unclear** — needs human judgement (see §4).

> This is a fund-safety deliverable. Statements are compressed for the table;
> the authoritative wording plus full citations live in the verdict record and in
> §3. Where a verdict and an invariant's own optimistic framing disagreed, the
> **verdict wins**.

## 3. Confirmed Gaps & Violations

Every partial invariant, ranked by residual severity. **None is fully safe.** Fix
directions are scope-only.

### HIGH

#### G1 — `icp-refund-failure-leaves-funds-recoverable` (fund-stranding)
- **Gap.** On ICP refund-leg failure the session is marked `#closed` (`Sessions.mo:862-864`) but `lastActivityAt` is NOT bumped (last set on voucher consume, `Sessions.mo:739`). `gcClosedSessions` deletes any `#closed`/`#expired` session once `now − lastActivityAt > 24h` (`Sessions.mo:1095-1109,1102`), and it runs every 60s (`Gateway.mo:960-964`). `recoverEscrow` needs the session record and returns "Session not found" once it is gone (`Sessions.mo:1286-1288`); no other API can move funds from the per-session subaccount.
- **Violation path.** A long-maxDuration session idle >24h is expiry-closed, its refund leg fails → `#closed` with `lastActivityAt` already older than the retention window → the same (or next) timer tick GC-deletes the record → `recoverEscrow(sessionId)` returns "Session not found" → escrow remainder permanently stranded.
- **Cite.** `Sessions.mo:862-864,1095-1109,1256-1290,739`, `Gateway.mo:960-964`.
- **Fix direction.** Bump `lastActivityAt` (or set a distinct "needs-recovery" timestamp) at close-time so retention is measured from close, and/or exclude refund-failed sessions from GC until recovered.

#### G2 — `job-buyer-identifies-actual-payer-and-rail-recorded` (pool insolvency + misdirected refund)
- **Gap.** The Candid submit path stores `buyer = Principal.toText(msg.caller)` (`example/main.mo:905`) unconditionally, but the Candid 402 quote mints EVM-capable nonces (`requireAll`→`requireEvm`), so `gate.settle(sig,null)` can take the EVM branch and land funds on-chain while the stored buyer is a principal (never `0x`). `evmJobRail` is therefore never recorded (`ServiceRegistry.mo:402`), so settle/refund draw the ICP ckUSDC pool for an EVM-funded job and refund to `msg.caller` (not the payer).
- **Violation path.** Client calls `submitServiceRequest(id, params, null)` → gets EVM PaymentRequirements → re-calls echoing an EVM nonce + EIP-3009 authz → `example/main.mo:902` settles on-chain → `createJobFromReceipt(Principal.toText(msg.caller), …)` stores a principal buyer with no rail → on settle/expire the operator is paid and buyer refunded from the ICP pool (drained; EVM funds stranded in the canister EVM address; refund misdirected).
- **Cite.** `example/main.mo:890,902,905`, `Gateway.mo:570,706`, `ServiceRegistry.mo:402,149,187,203,971`.
- **Fix direction.** On the Candid submit path, bind the stored buyer/rail to the settle receipt (`receipt.sender` + `receipt.network`) as the HTTP path does, or reject EVM-rail settles when the caller is a principal.

#### G3 — `maybesent-collapse-only-with-onchain-replay-protection` (latent double-pay footgun)
- **Gap.** The published `Gateway.sendErc20Transfer` (`Gateway.mo:916-927`) collapses `#maybeSent→#err` on the **outbound, replay-unprotected** ERC-20 rail — exactly the collapse the invariant forbids off the inbound EIP-3009 path. Documented UNCONFIRMED; **no in-repo caller** (internal outbound paths use `sendErc20TransferConfirmed`, which parks `#maybeSent` as `#pending`).
- **Violation path.** An external consumer wires `Gateway.sendErc20Transfer` into an outbound settle/refund. A `#maybeSent` (post-dispatch error / `#Inconsistent` / `#NonceTooHigh`) is reported as `#err` (="not broadcast, safe to retry"); the consumer re-broadcasts; with no on-chain replay protection the transfer executes twice.
- **Cite.** `Gateway.mo:916-927`, `EvmSender.mo:188-190,271,279,283,335-357`.
- **Fix direction.** Deprecate/remove the public `#maybeSent→#err` outbound helper, or make it return `#pending` (park) like the confirmed variant, so no external caller can inherit the unsafe collapse.

#### G4 — `sweep-and-marketplace-not-reconciled-against-cap` (pool insolvency; documented residual)
- **Gap (by design, documented).** The accounting cap is enforced only on session *opens* (`EvmEscrow.allocate`). `sweepEvm` (`example/main.mo:1166-1174`) and marketplace `settleToOperator`/`refundOnRail` (`ServiceRegistry.mo:148-214`) spend from the **same** shared EVM address via the same hook without consulting `totalAllocated`/`poolCap`.
- **Violation path.** With open sessions holding allocations fully backed on-chain, a controller `sweepEvm` of an operator-chosen amount, or a burst of marketplace EVM outflows, drains the shared balance below `totalAllocated`; a later session-close refund fails/strands → insolvency for open sessions.
- **Cite.** `example/main.mo:1166-1174,163,134`, `ServiceRegistry.mo:148-214`, `EvmEscrow.mo:40-57,60,77`, `docs/security-model.md:67-74`.
- **Fix direction.** Add a system-wide on-chain-balance reservation (reconcile sweep + marketplace outflows against `totalAllocated`), or keep it an operator contract but surface a live "sweepable surplus = balance − totalAllocated" figure. (Currently an explicit operator responsibility.)

### MEDIUM

#### G5 — `FAILED-MEANS-NO-FUNDS-MOVED` (fund-stranding + possible payer double-pay)
- **Gap.** `executeTransferWithAuthorization` folds `#maybeSent→#err(m.reason)` (`EvmSender.mo:396`), discarding `m.txHash`. So `Gateway.settle`'s `#err` arm returns `#settlementFailed` with **no txHash** even though the inbound EIP-3009 tx may have been broadcast and could later mine.
- **Violation path.** Ambiguous broadcast (`#Inconsistent` / post-dispatch exception / `NonceTooHigh`) → `#err` arm unlocks nonce + releases daily + returns `#settlementFailed` with no recovery handle → tx mines (payer→canister) → same-authz retry reverts, but a normally re-signed authz (fresh EIP-3009 nonce) double-pays; payer funds stranded with no poll hash. (Canister-side no-double-pay still holds via on-chain single-use nonce; receipt only on `#confirmed`.)
- **Cite.** `Gateway.mo:688-693`, `EvmSender.mo:271,279,283,345,389-397`.
- **Fix direction.** Preserve `m.txHash` on the inbound `#maybeSent` collapse (surface a `#settlementPending`-style hash) so an ambiguously-broadcast-then-mined deposit is trackable/refundable rather than silently stranded.

#### G6 — `pending-evm-deposits-tracked-and-refunded-only-if-mined (M8)` (fund-stranding)
- **Gap.** Refund-if-mined is correct, but the **tracking** half misses the `#maybeSent` case: `openEvmSession`'s `#err` arm deallocates and returns `#settlementFailed` with **no** `pendingEvmDeposits.put` and no txHash in the message (`Sessions.mo:586-593`), because `executeTransferWithAuthorization` dropped the hash (`EvmSender.mo:396`).
- **Violation path.** Inbound session deposit ambiguously broadcast → `#err` arm → no tracker entry → deposit later mines into the shared pool → `reconcileEvmDeposit(txHash)` returns `#notFound` → payer funds stranded, no automatic refund.
- **Cite.** `Sessions.mo:571-593,1070-1092`, `EvmSender.mo:389-398`.
- **Fix direction.** Same root as G5 — carry the broadcast hash through the inbound collapse and record it in `pendingEvmDeposits` on the `#maybeSent` path too.

#### G7 — `GLOBAL-ADMISSION-METERING` (unmetered ecRecover DoS)
- **Gap.** The three enumerated ecRecover paths are metered by one global bucket, but `ServiceRegistry.confirmJobEvm`/`disputeJobEvm` run attacker-controlled 65-byte ecRecover with **zero** admission metering (no admitRate/cycle-floor in the module).
- **Violation path.** With any `#Submitted` job (predictable `job-N` id), an attacker loops `confirmJobEvm('job-N', garbageSig)`; each call runs unmetered keccak+secp256k1 recover; failed auth leaves status `#Submitted`, permitting unbounded repeats → cycle drain toward freeze on a rail the global bucket never touches. (Not exposed in `example/main.mo`, but public in the library.)
- **Cite.** `ServiceRegistry.mo:671-687,700-723,377-378`, `Gateway.mo:104-122`.
- **Fix direction.** Route the ServiceRegistry EVM-buyer ecRecover through the same injected admit-rate hook used for `openEvmSession`.

#### G8 — `daily-release-targets-open-day-bucket` (over-spend past daily cap)
- **Gap.** `spendDay` is transient and reset to `policy.currentDay()` on load (`Sessions.mo:1338`), while `dailySpend` buckets persist with their original day keys. An upgrade crossing a UTC day boundary retargets the release to the wrong bucket.
- **Violation path.** Day N: session opens, deposit reserved into `dailySpend[N]`, `spendDay=N`. Upgrade lands on day N+1 → `spendDay` rebuilt as N+1. On close, `releaseDaily(payer, N+1, D−C)` decrements the unrelated N+1 bucket (day-N reservation stranded) → frees up to `D−C` of day-N+1 headroom → payer over-spends past `maxPerDay`. Gated on `maxPerDay` being configured.
- **Cite.** `Sessions.mo:343,632,1338`, `Types.mo:293-295,317-330`, `Policy.mo:35,182-187,404-421`.
- **Fix direction.** Persist `spendDay` in `StableSession` (or persist a stable open-day marker) so release always targets the day the reservation was recorded.

#### G9 — `recipient-address-validated-pre-broadcast (M9/L21)` (fund loss on sign-only rail)
- **Gap.** The two cited EvmSender sites are correct, but the sibling **sign-only** rail `EvmSigner.signErc20Transfer` decodes the recipient (`EvmSigner.mo:171`) with **no 20-byte check** before encoding it into `transfer()` calldata and signing; `signTransaction` validates only the *token* address, not the calldata recipient.
- **Violation path.** Call `signErc20Transfer` with a truncated even-length-hex recipient (e.g. 19 bytes) → `natToBytes(bytesToNat(...),32)` silently left-extends it into a shifted/zero wrong address → signed with the canister ECDSA key → broadcast → tokens sent to the wrong/zero address.
- **Cite.** `EvmSigner.mo:161-180,171,175,179,133`, `EvmSender.mo:311-313`.
- **Fix direction.** Mirror the `EvmSender.sendErc20Transfer` 20-byte recipient guard into `EvmSigner.signErc20Transfer` before building calldata.

#### G10 — `settled-amount-equals-the-quoted-total` & G11 `quote-challenge-…-price-coherence` (operator underpayment / price bypass)
- **Gap (shared root).** The two service-rail settles pass `null` as `expectedAmount` (`example/main.mo:556,902`), so `Gateway.mo:549-557`'s cross-resource amount-equality guard is skipped; the nonce is bound only to (amount,network,token), not serviceId. `validateSubmittable` checks a caller-supplied constant, not the nonce-bound amount.
- **Violation path.** Attacker gets a cheap live nonce (cheap service's 402, or `/search` at 1_000) on the same network/token, then submits it to an expensive service. `validateSubmittable` passes (checks the correct expensive total constant); `settle(sig,null)` settles the cheap bound amount; `createJobFromReceipt` records `job.amount = cheap receipt.amount`. Buyer cannot over-pay (they chose the nonce), but the expensive job is escrowed/paid-out for less than price+fee → operator underpayment. Pool stays balanced (self-balancing), so severity is medium not high.
- **Cite.** `example/main.mo:552,556,890,896,898,902`, `Gateway.mo:544-560,549-557`, `ServiceRegistry.mo:353-357,388,481`.
- **Fix direction.** Pass `?(svcPrice + CKUSDC_FEE)` (not `null`) to `gate.settle` on both service-rail sites, matching the `/content` and `/search` paths.

#### G12 — `session-priced-services-never-take-per-request-charge` (per-request charge on a session service)
- **Gap.** The HTTP 402 branch and the Candid no-signature branch reject `#Session`, but the Candid `?sig` arm (`example/main.mo:893-902`) has no `#Session` guard, and `validateSubmittable`'s `#Session` case is a no-op returning `#ok`. With `expectedAmount=null` the cross-resource nonce guard is disabled.
- **Violation path.** Buyer signs a payment for another resource, then submits it to `submitServiceRequest(sessionServiceId, params, ?sig)`; `validateSubmittable` `#ok`; `settle(sig,null)` locks/settles the other resource's nonce; `createJobFromReceipt` creates a job for the SESSION service → a per-request charge taken against a session-priced service. (Stock-EVM no-nonce case is safe → `#expired`.)
- **Cite.** `example/main.mo:884-902`, `ServiceRegistry.mo:364,375`, `Gateway.mo:544-567`.
- **Fix direction.** Add an `amount == 0 ⇒ #error(session billing)` guard in the `?sig` arm (mirror the null-branch guard), or make `validateSubmittable` reject `#Session`.

#### G13 — `same-rail-settlement (C3)` (cross-rail draw / stranding on pre-1a migration)
- **Gap.** Rail↔0x-buyer equivalence is set only at job creation and stored in a side map. EVM (0x) buyers existed (commit 319bb56) before the rail map (commit 4459ddc). `loadStable` decodes a pre-1a blob's absent `evmRails` to an empty map (`ServiceRegistry.mo:1099-1102`).
- **Violation path.** Non-terminal 0x-buyer job carried across a pre-1a→current upgrade keeps its 0x buyer but has no rail entry. Settle takes the null-rail ICP branch → operator paid ICP from the pool for an EVM-funded job (C3 re-introduced); refund hits `buyerIcpAccount`→null→`#err` and strands. Bounded to the migration window.
- **Cite.** `ServiceRegistry.mo:402-404,149-180,168-178,186-214,326-330,1099-1102`.
- **Fix direction.** Add a one-shot migration that backfills `evmJobRail` for any stored `0x` buyer during load (needs human confirmation that a pre-1a deployment with in-flight EVM jobs exists — see §4).

#### G14 — `REFUND_ONLY_ON_PROVEN_NO_SETTLE` (cap under-count → retry double-pay)
- **Gap.** `settleMayHaveMoved` recognizes only a marker-tagged `Ic402Error`, but the MCP catch blocks catch *all* throws. A raw lost-response/timeout after the canister already committed the settle is neither an `Ic402Error` nor marker-tagged, so `refundSpend` runs and un-counts a spend that moved on-chain.
- **Violation path.** Confirmed `submit_request`: gate commits reservation → `submitServiceRequest` settles (block index) and creates job, but response is lost → raw non-`Ic402Error` propagates → `settleMayHaveMoved(e)` false → `refundSpend(reservedAmount)` un-counts a real spend → retry re-probes with fresh nonce and settles again = double-pay past the cumulative cap.
- **Cite.** `index.ts:112-114,744-746,1448-1455`, `client.ts:736-808`, `docs/decisions/settled-then-job-failed.md:64`.
- **Fix direction.** On an unknown/untagged throw after the confirm gate, KEEP the reservation (fail toward over-counting) rather than refunding.

#### G15 — `PAYMENT_HEADERS_ONLY_TO_VALIDATED_PUBLIC_TARGETS` (SSRF via redirect on register_agent RPC)
- **Gap.** `fetch_x402` re-validates every redirect hop, but `register_agent`'s custom `rpcUrl` is validated once (`index.ts:1279-1290`) then handed to viem's `http(rpcUrl)` (`packages/client/src/evm.ts:480-483`), whose default fetch follows HTTP redirects with no per-hop re-validation or pinned IP.
- **Violation path.** Agent supplies a public attacker-controlled `rpcUrl`; the RPC answers the JSON-RPC POST with a 30x to `http://169.254.169.254/` (or internal host); viem follows it → getTransactionCount/getBlock/broadcastTransaction POSTed to an unvalidated internal/metadata target → MCP-host SSRF. (Not a payment fund loss; no signed header on this rail.)
- **Cite.** `index.ts:1279-1290`, `packages/client/src/evm.ts:480-483,604-607,621`, `security.ts:161-185,195-219`.
- **Fix direction.** Route register_agent RPC through a redirect-revalidating transport (manual redirect + `assertResolvedHostIsPublic` per hop), as the fetch_x402 `safeFetch` path already does.

### LOW

#### G16 — `CROSS-RESOURCE-AMOUNT-GUARD` (operator-visible underpayment)
- **Gap.** Reference wiring does NOT always pass `?amount`: the two service-request settles pass `null` (`example/main.mo:556,902`), skipping the guard (`Gateway.mo:556` no-op). Same root as G10.
- **Violation path.** As G10; escrow self-balances so no insolvency/double-pay — residual is voluntary, visible operator underpayment on a cross-resource job.
- **Cite.** `Gateway.mo:549-557`, `example/main.mo:556,902`, `ServiceRegistry.mo:388,481-488`.
- **Fix direction.** Same as G10 (pass `?amount`).

#### G17 — `TWO-OF-N-RPC-CONSENSUS-FOR-TRUTH` (inaccurate citation + latent inconsistency)
- **Gap.** The min=2 truth invariant holds on every *live* production RPC interaction. But two claimed details are wrong: `EvmVerify.verifyTransaction` passes `null` RpcConfig (not `#Threshold{min=2}`) at `EvmVerify.mo:104`, and its token/recipient/amount receipt checks are **not on the production path** (no callers; `docs/security-model.md:45`).
- **Violation path.** None today (verifyTransaction is dead code). If it were ever wired onto a fund path for a 2-provider chain, a single malicious provider could return a fabricated receipt and `verifyTransaction` would `#ok`.
- **Cite.** `EvmVerify.mo:9,102-159`, `EvmSender.mo:114-119`.
- **Fix direction.** Either give `verifyTransaction` the `#Threshold{min=2}` config or delete it, and correct the module header claiming it's "Used by Gateway.settle()".

#### G18 — `ICP-SENDER-PARSE-SAFETY` (settle-message DoS via trap)
- **Gap.** `Principal.fromText` **traps un-catchably** on bad input in Motoko; the `try/catch` at `Gateway.mo:754-759` cannot catch a trap (the codebase's own `ServiceRegistry.mo:306-311` uses a structural validator for exactly this reason). Only the length gate (`Gateway.mo:750`) is effective.
- **Violation path.** settle with `network="icp:1"`, a valid nonce, configured ledger, and `sender` = any ≥5-char non-principal string (e.g. "hellox") → passes length gate → `Principal.fromText` traps → settle message rejects instead of returning `#invalidSignature`. State rolls back (no fund loss); liveness/contract violation only.
- **Cite.** `Gateway.mo:750,754-759`, `ServiceRegistry.mo:306-311`, `base/Principal.mo:125`.
- **Fix direction.** Replace the try/catch with a structural principal validator (reuse `looksLikePrincipal`) before `Principal.fromText`.

#### G19 — `RECEIPT-ID-UNIQUENESS` (constant placeholder id on expiry sweep)
- **Gap.** `closeSessionInternal` builds receipts with placeholder `id="rcpt-close"` (`Sessions.mo:887,1240`), meant to be re-stamped by `Gateway.closeSession`/`forceCloseSession`. But `Gateway.closeExpiredSessions` (`Gateway.mo:891-893`) and the timer forward the array unchanged, so timer/expiry-swept receipts all carry the literal `rcpt-close`.
- **Violation path.** Call `closeExpiredSessions` with 2+ expired sessions (or let the timer fire) → returned receipts collide on `rcpt-close`, and every sweep across upgrades reuses it. Library doesn't key settlement on receipt.id, so no internal double-pay; risk is a downstream consumer keying on receipt.id.
- **Cite.** `Gateway.mo:891-893,961,189-192`, `Sessions.mo:887,946,1240`.
- **Fix direction.** Re-stamp each ok receipt via `nextReceiptId` inside `Gateway.closeExpiredSessions`, as the single-session paths do.

#### G20 — `daily-spend-reserved-once-at-open-not-per-voucher` (bounded self-cap overshoot)
- **Gap.** The open-vs-open serialization holds via the per-caller open lock, but the charge rail never touches `sessionOpenLocks` and the open path doesn't re-check the daily limit after its deposit await. A same-caller `Gateway.settle` during the open's deposit await writes the same per-caller daily bucket.
- **Violation path.** maxPerDay=100, spend 0. openSession checks 0+60≤100, awaits deposit. During the await, caller's `Gateway.settle` records 60 → bucket=60. openSession resumes (no daily re-check) → records deposit 60 → bucket=120 > 100. Over-spend of the caller's own self-cap using their own funds; no theft/double-pay/insolvency.
- **Cite.** `Sessions.mo:259,300,313-334,366`, `Gateway.mo:761,772`.
- **Fix direction.** Re-check the daily limit after the deposit await (as maxConcurrent is), or have the charge rail respect the open lock.

#### G21 — `finalize-releases-pool-and-daily-reservations-exactly-once` (bounded daily over-credit)
- **Gap.** `releaseDaily` is non-idempotent (`Policy.mo:182-187`), but the EVM close success path does not re-fetch/re-check status after its settle/refund awaits before releasing (unlike `reconcileSession`, which does at `Sessions.mo:1024-1026`). Deallocate is idempotent, so pool stays solvent.
- **Violation path.** Payer closes an EVM session (`#closing`, suspends at settle await). Controller `forceResolveSession` runs during the await → finalizes (releaseDaily once, `#closed`). Close resumes and runs releaseDaily a second time (`Sessions.mo:1228`) on the same `D−C` → payer's daily bucket over-credited → over-spend past the daily cap. Requires a trusted controller + precise timing.
- **Cite.** `Sessions.mo:988-993,1006,1024-1030,1144,1181,1228`, `Policy.mo:182-187`, `EvmEscrow.mo:60-62`.
- **Fix direction.** Re-fetch + re-check `status == #closing` after the settle/refund awaits in `closeEvmSessionInternal` before deallocate/releaseDaily.

#### G22 — `FUNDS_MOVED_FLAG_FIDELITY` (marker missing on some post-settle arms)
- **Gap.** The fund-safety half holds (refund guard relies only on the structured flag; guarded consumers emit the marker on their only moved-funds arm). But the *universal* claim is false: `getContent` has three post-`#ok`-settle arms omitting the marker (`example/main.mo:714,719,725`). Not consumed by any refund guard today (the generic call tool is read-only; `client.call` returns raw `#error` without setting fundsMoved).
- **Violation path.** getContent settles (`example/main.mo:710`), content deleted concurrently, post-settle re-fetch returns null → `#error("Not found")` with no marker → a buyer's settled payment stranded with no delivery/refund. If ever surfaced via settleError, fundsMoved=false → over-refund.
- **Cite.** `example/main.mo:706-725`, `client.ts:107,115,203`, `index.ts:113,1527-1559`.
- **Fix direction.** Emit the "do NOT retry payment" marker on every getContent arm reached after `gate.settle` returns `#ok`; also convert openSession's `#err(_)` wildcard to an exhaustive match (as submit does).

#### G23 — `TWO_PHASE_CONFIRM_ON_ALL_VALUE_MOVERS` (settle/broadcast reachable without confirm)
- **Gap.** All enumerated tools enforce the gate, but the universal clause fails: the generic `call` tool reaches `getContent` via the `get`-prefix fallback (`guards.ts:285`; "getcontent" hits no block substring). `getContent(id, ?sig)` with a signature is a settling update (`example/main.mo:710` settles + on EVM broadcasts gas).
- **Violation path.** MCP `call` → `isCallMethodAllowed` admits `getContent` via get-prefix → `actor.getContent(id, [sig])` with NO requireConfirmation/cap → settles + broadcasts. Low severity: pays INTO the operator's own canister, LLM can't forge the buyer signature, only operator gas cost, settle replay-protected. Documented (M16, `guards.ts:265-269`).
- **Cite.** `index.ts:1550-1572`, `guards.ts:244-292,265-269`, `example/main.mo:691-742`.
- **Fix direction.** Add `getContent` (dual-mode settling reads) to `CALL_BLOCK_SUBSTRINGS`/deny-list, or expose a dedicated capped+confirmed purchase tool and block the generic-call reach.

No verdict returned `unclear`; every audited invariant is enforced or partial. The
items below are judgement calls the verification surfaced that need a **human
decision**, not a code fact:

   live depends on whether any deployed canister ran a pre-`4459ddc` (rail-map)
   build with in-flight EVM-buyer jobs and will upgrade forward. If no such
   deployment exists, G13 is theoretical. *Needs deployment-history confirmation.*
   Cite: `ServiceRegistry.mo:1099-1102`.

   it is a public library API documented UNCONFIRMED. Decide whether to keep it
   (with a hard warning) or remove it — a library-consumer policy call.
   Cite: `Gateway.mo:916-927`.

   reference `example/main.mo` exposes only the principal-based variants, so the
   unmetered-ecRecover DoS is not reachable in the reference wiring — but the EVM
   variants are public in the published library. Whether a consumer will expose
   them determines urgency. Cite: `ServiceRegistry.mo:700-723`.

4. **Operator-contract residuals (G4 and `operator-funds-pool-at-cap`).** Shared
   EVM pool solvency is a *documented operator invariant*, not code-enforced.
   Human sign-off needed on whether to promote it to code (balance reconciliation)
