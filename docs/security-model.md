# ic402 security model

**Who this is for**

- **Integrators** (Motoko devs embedding the library) — read §1–§3. The library is **not secure‑by‑default**; §2 is a checklist you must implement.
- **Operators** (running an ic402 canister with real funds) — read §3–§5. Your controller key *is* the security boundary.

## TL;DR

- The **money paths are sound.** Recipient binding, exact `value == amount`, single‑use nonces, and confirm‑before‑deliver were all re‑verified adversarially (§1).
- The **library ships the mechanism; the example ships the policy.** Four security‑critical checks live *only* in [`example/main.mo`](../example/main.mo). Copy them or inherit a price‑bypass / roster‑leak / content‑leak (§2).
- **One trust root.** Every admin/signer/recovery power is `Principal.isController`. A single stolen controller key = total EVM drain + unlimited arbitrary signing. There is no operator‑vs‑controller separation (§4).
- **EVM finality is depth‑0** and RPC trust is **2‑of‑N** over public endpoints — fine for low‑value L2 USDC, not for high‑value or reorg‑prone settlement (§3).

## 1. What you get for free (already defended)

The *unprivileged* attack surface is well defended. These were probed adversarially and held:

- **Recipient binding (C‑1).** EVM settlement requires the EIP‑3009 `authorization.to` to equal the canister's own derived EVM address — a payer can't make the canister pay gas for a self‑transfer and still get a receipt.
- **Exact value.** `authorization.value` must *equal* the required amount (x402 v2 §6.1.2), not merely cover it — overpayment is rejected.
- **Replay.** Server nonces are single‑use and bound to `(expiry, amount, network, token)`; the EVM rail also relies on the on‑chain single‑use EIP‑3009 nonce and EIP‑155 chain‑id.
- **Finality before delivery.** `settle()` issues a receipt only on a confirmed (`status == 1`) transaction; a mempool ack is not treated as settlement.
- **Double‑broadcast safety.** `EvmSender` holds a synchronous `txInProgress` single‑flight lock, so two concurrent settles can't both reach `transferWithAuthorization`. Since 2.22.0 it also broadcasts each EIP‑3009 authorization at most once (§3).
- **DoS floor.** The unauthenticated facilitator endpoints run behind a 500B‑cycle floor (and a global rate bucket) *before* any attacker‑controlled parsing / `ecRecover` / RPC / signing work.
- No inter‑`await` reentrancy gap and no value‑moving integer underflow were found.

## 2. Integration checklist — the library is **not** secure‑by‑default

The `Gateway`, `Policy`, and `ContentStore` modules intentionally ship **without access control** so you can wire your own auth model. `example/main.mo` is the reference wiring. If you embed the library, you **must** add these four — each one absent is a concrete exploit:

| # | Guard | What the library leaves open | What to do (see `example/main.mo`) | If you skip it |
|---|-------|------------------------------|------------------------------------|----------------|
| 1 | **Policy‑mutation auth** | `Gateway.setPolicy` / `Policy.setGlobalPolicy` perform no caller check (the source even warns: *"MUST restrict access… `assert(Principal.isController(msg.caller))`"*). | Gate your `setPolicy` with `assert(Principal.isController(msg.caller))`. | Anyone rewrites your spend/rate limits to zero or adds themselves to an allowlist. |
| 2 | **Roster redaction** | `Policy.getGlobalPolicy()` returns the raw allow/block lists. | In any **public** read, redact the rosters (the example's `getPolicyConfig`, SEC‑4). | You leak your access‑control roster. |
| 3 | **Cross‑resource underpayment** | A server nonce binds `amount/token/network` but **not** the resource. | After `settle`, check `receipt.amount >= thisResourcePrice` (the example's `getContent` does exactly this). | A cheap nonce unlocks an expensive resource. |
| 4 | **Content access control** | `ContentStore.get` / `getChunk` decrypt for **any** caller — they take no caller argument. | Deliver only behind a settled payment or a valid grant (the example gates `getContent` on `gate.settleFrom`). | Free content. |

- **Candid settle paths (2.17.0):** call `gate.settleFrom(msg.caller, sig, expected)`, not `settle` — on the ICP rail `signature.sender` is only a claim, and `settleFrom` refuses a payment whose sender is not the caller. HTTP paths have no caller and stay allowance‑authenticated — except that the canister itself is never accepted as the payer (2.22.0: the ledger skips the allowance check when `from` is the caller's own account, so before 2.22.0 anyone could have such a payment drawn from the canister's own funds): tell payers to approve exactly amount + fee with an expiry (`@ic402/client` ≥ 2.17.0 does), or a stranger holding a live nonce can spend a standing allowance — through the HTTP twin of a Candid route too, so the Candid fix does not protect a standing allowance on a canister serving both. The same junk HTTP settles also hold the named payer's daily reservation (`maxPerDay`) while each ledger call is in flight: enough at once (the example: ~100 × 5,000 against 500,000) refuse the payer's own settles and session opens until they fail. 2.17.0's I6 fix frees the rate slot, not this. Since 2.22.0 none of them holds it past its call: an HTTP settle whose ledger call is rejected with an unknown outcome now releases it too (a `settleFrom` keeps it, §2b), so junk settles during a ledger outage no longer fill the payer's limit. Nonces are predictable and not bound to a payer, so a stranger can also start a settle of the payer's own payment. Since 2.22.0, while an attempt naming a **different** payer holds the nonce, the payer's settle answers busy (`#policyDenied("A settlement with this payment is already in progress — retry this same payment …")`): that stranger can make the payer wait one ledger round‑trip, but not turn the payer's settle into a "funds may have moved" answer. An attempt naming this payer (the payer's own re‑send, or a stranger's HTTP settle naming the payer) answers `#settlementPending` until it returns, because it may be moving the payer's funds.
- **Session endpoints (2.17.0):** call `gate.consumeVoucherFrom(msg.caller, voucher)`, then `setSignedVoucherFallback(false)` once every client is on SDK ≥ 2.17.0 (the example does). Until then the legacy path is today's exposure: anyone who knows an open session id can make the canister run the ~420M‑cycle signature check and spend the payer's per‑minute rate slot. 2.17.0 hardens nothing here until the fallback is off.
- **Job reads (2.22.0, example):** `getJob` and `getJobResult` answer only the job's buyer, its operator or a controller (job ids are sequential, so they are easy to guess); anyone else gets `null`, and `getJobStatus` stays public. An EVM‑paid buyer (a `0x` address) has no principal to call as, so it loses result reads. Copy this gate if your canister exposes jobs.

**Also:** every "admin/timer" library method ships with no auth and says so in‑source (*"WARNING: this method performs no access control"*) — `forceCloseSession`, `forceResolveSession`, the `reconcile*` hooks, `sweepEvm`, `signTypedData`. Controller‑gate **every one** you expose publicly.

> The README quick‑start is deliberately minimal. Treat [`example/main.mo`](../example/main.mo) — not the quick‑start — as the secure baseline to copy.

## 2b. ICP‑rail: a rejected ledger call is not "not paid" (2.20.0)

- **A reject does not prove the transfer failed.** The DFINITY ICP and ICRC‑1 ledgers commit a transfer and then await `archive_blocks` inside the same call, so a trap after that await rejects a transfer that landed. A stopped ledger answers with the same code (`CANISTER_ERROR`).
- **What ic402 does.** Only rejects the system raises before the ledger runs (`#destination_invalid`, `#system_transient`, `#call_error`; `Utils.rejectedBeforeExecution`) count as nothing moved. Any other reject:
  - **`settle` / `settleFrom`** return `#settlementPending`. The nonce stays locked. The daily reservation stays held for a `settleFrom` charge only; since 2.22.0 an HTTP `settle` releases it, since its `sender` is only claimed. **Do not deliver, and do not ask for a new payment** until it is resolved (recovery runbook, §7).
    - **Busy vs pending (2.22.0).** A settle of a payment whose nonce is held in flight by an attempt naming a **different** payer (ICP `sender`; EVM authorization `from`, in any hex spelling) answers `#policyDenied("A settlement with this payment is already in progress — retry this same payment …")`: nothing of this payer's is known to have moved. Retrying the same payment shortly is preferred; paying anew is also safe. The same payer's own duplicate in flight answers `#settlementPending`, as in 2.21.0, since its funds may be moving; so does an attempt whose outcome is unknown, and a lock restored after an upgrade (nothing is in flight across one). The SDK treats the busy answer as retryable with the same payment.
    - **2.21.0, `setLedgerDedup(true)`:** every charge first queries the ledger's fee, so a stopped ledger refuses the charge cleanly (nothing moved, safe to retry). It also carries that fee, the nonce as memo and a `created_at_time`. For a charge made through **`settleFrom`** (the caller is the payer), the canister keeps the transfer; the payer's `settleFrom` with the same payment re‑sends it unchanged, and the ledger's deduplication answers `#Duplicate` (it was charged) or `#Ok` (charged now): one receipt either way. Another caller, network or price sends nothing. Charges made through **`settle`** (HTTP) keep nothing: there `sender` is only a claim and nonces are not secrets, so letting a re‑submit resolve would let anyone who saw the nonce on the ledger collect the payer's receipt. The setting is an **operator declaration**: ICRC‑1 makes deduplication a SHOULD, and no ledger API declares it, so on a ledger that does not deduplicate a re‑send charges twice. Default off.
    - **Setting off, HTTP charges,** or after the ledger's 24‑hour window, a fee change or an upgrade: a re‑submit is answered as pending, and the charge is resolved by checking the ledger. The nonce stays locked until the nonce clean‑up (at 10,000 live or every 20,000 issued nonces) removes it after expiry; a nonce with a kept transfer is kept 24 hours longer, and since 2.22.0 so is a nonce whose settlement is still in flight.
  - **HTTP:** the example's x402 routes return the 402 `SettlementResponse` with `errorReason = "settlement_pending"`, which `@ic402/client` and the MCP server turn into an error with `fundsMoved = true` (do not pay again).
  - **Session close (settle leg)** leaves the session `#closing` (also `#settlementPending`). The controller's `reconcileSession` then reads the escrow balance: the full deposit means nothing was paid, so it reopens; less means the settle landed, so it closes with the remainder owed to the payer. Use it before `forceResolveSession`, which strands the recipient's share if the settle never landed.
  - **ServiceRegistry payouts** (2.19.1) leave the job `#Settling` for a controller to check and `resolveJob`.
- **Session open (2.21.0).** `openSession` first queries the ledger's fee; if that fails (a stopped ledger) the open is refused and nothing moves. A reject on the deposit pull after that, other than one raised before the ledger ran, parks the session `#closing` with nothing consumed, so the record exists. `reconcileSession` reads the escrow balance: the deposit is there, so it opens; it is not, so it closes with nothing owed. Before 2.21.0 the reject escaped `openSession` and a deposit that had landed had no session record.
- **Not covered.** If a deposit lands but the payer's concurrent‑session limit was reached meanwhile, `openSession` refunds it before any record exists; if that refund fails, the deposit sits in escrow with no session record (unchanged).
- **Session recovery and closes (2.22.0).**
  - **`recoverEscrow` is bounded by the refund‑owed entry.** It pays only against the session's entry (written by a close whose refund failed, by `reconcileSession`, and by `forceResolveSession`), never more than the entry in total, one recovery per session at a time, and from the session's own ledger only. **Persisting `refundOwedToStable()` / `loadRefundOwed` is now required:** without it, every upgrade takes away the payers' in‑band recovery.
  - **A session's token resolves to the ledger holding its deposit.** A new open's token must be a configured ledger's principal text, a configured token's exact symbol, or `icp:*`; anything else is refused (`#tokenNotAccepted`), and a symbol is stored as its ledger's principal text. At close, `reconcileSession` and `recoverEscrow`, a stored token resolves as: a configured ledger's principal text → that ledger; a principal text that is not a configured ledger → fails closed, the session left as it was; anything else (a symbol or other text stored before 2.22.0, `icp:*`) → the first configured ledger, where 2.21.0 put the deposit. A fail‑closed principal has two causes: its ledger was removed from the configuration, or the session was opened before 2.22.0 with an unconfigured principal and its escrow is on the ledger that was then first. The refusal names both; check which ledger holds the escrow before changing the configuration, and close such pre‑2.22.0 sessions before upgrading.
  - **A live close is left alone.** `forceResolveSession` and `reconcileSession` refuse a session whose close is still in flight, on both rails: "A close of this session is still in flight — call again once it returns".

## 3. EVM‑rail trust assumptions (integrators + operators)

- **No confirmation‑depth / reorg protection.** `confirmTransaction` treats `status == 1` at the chain tip as final, on *both* the inbound (you got paid) and outbound (you refunded) directions. A shallow reorg can un‑mine a credited payment or a confirmed refund after value was delivered. (`#Safe`/`#Finalized` block tags exist but are unused — blocked by the absence of `eth_getBlockByNumber` in the RPC interface.) Practically low‑risk for optimistic‑L2 USDC; real for L1 or high value.
- **RPC trust is 2‑of‑N consensus** over hardcoded public, no‑auth endpoints (for Avalanche + testnet L2s). A 2‑of‑3 provider coalition could forge a "confirmed" receipt. The live path checks only `status == 1` and re‑derives nothing from the mined receipt (the thorough log re‑verifier `EvmVerify.verifyTransaction` is not on the production path).
- **One broadcast per authorization (2.22.0).** The sender keeps one claim per chain, token, payer and authorization nonce, taken before the send and released only if nothing was broadcast. A replay of an authorization this canister already broadcast is refused as pending (`#settlementPending`, naming the earlier tx), and the server nonce it came with is unlocked, since nothing of it moved. A broadcast call that is itself rejected keeps the claim and answers `#settlementPending` (it may have broadcast). The claims are transient: an upgrade allows one more broadcast per authorization.
- **A revert is checked against `authorizationState` (2.22.0).** Anyone can submit `transferWithAuthorization`, so the canister's tx can revert because another tx used the authorization first. Settle and session open therefore read the token's `authorizationState`: still unused → failed, nothing moved; used, or unreadable → `#settlementPending`, with no receipt and no session. The read is at the latest block, so a lagging pair of providers can still answer "unused" for an authorization another tx has just used.
- **Tokens on one chain must be interchangeable (2.22.0).** The payer chooses the token and prices are compared in raw units. Every token listed on one chain must have the same decimals — enforced: a mixed chain traps the constructor (install or upgrade fails) and `setEvmChains` returns `#err` — and the same unit value, which is the **operator's** duty.
- **EVM policy principals are case‑insensitive (2.22.0).** An EVM payer's spending and rate buckets and its blocklist entry key on the lower‑cased address. Build blocklist entries with `Ic402.evmPolicyPrincipal(address)`; rebuild any entry made from a checksum‑case address.
- **Implication:** size EVM payments to what depth‑0 finality and 2‑of‑N RPC can safely carry. For high value, prefer the ICP rail or add your own confirmation‑depth gate.

## 4. Key custody & blast radius (operators)

- **One key, everything.** The canister derives a single tECDSA key (`derivation_path = []`) used for all EVM signing, all chains, all users — there is no per‑user key isolation.
- **The controller principal *is* the security boundary.** In the example, every fund/key/recovery method is `assert(Principal.isController(msg.caller))`:
  - `sweepEvm` — drains the **entire** EVM balance to any address (no balance check);
  - `signTypedData` — a **blind EIP‑712 oracle**: signs any 32‑byte `domainSeparator + structHash`, bypassing every spend cap;
  - `setPolicy` and the reconcile / force‑resolve recovery hooks.
- **Therefore a single stolen controller key = total, irreversible loss** (full EVM drain + arbitrary signing). Treat the controller like a hot wallet's private key: minimize the controller set, prefer a threshold/multisig or SNS/NNS‑style controller for funded mainnet canisters, and never leave a funded canister controlled by a single dev key.

## 5. Other operator notes

- **Content at rest.** ChaCha20‑Poly1305 (RFC 8439) is real, but the master key sits in **plaintext stable memory** — recoverable by any controller or via a state snapshot. "Only the canister can decrypt" holds against node operators and raw memory dumps, **not** against a controller. Don't store data whose confidentiality must survive controller compromise.
- **Facilitator / paid‑settle DoS.** The expensive EIP‑3009 `ecRecover` on every unauthenticated path — `/verify`, `/settle`, paid `/content` & `/search`, and EVM session‑open — is rate‑limited by a single **global** token bucket (~120/min) *inside* `settle`/`verifyPayment`/`openEvmSession` (so it doesn't depend on the consumer remembering to gate); a ~500B‑cycle floor backstops the facilitator HTTP routes. The bucket is transient (resets on upgrade) and un‑keyed (one client can consume the whole budget) — it bounds the rate of drain, not fairness, and not what each request costs. **2.23.1:** past the `ecRecover`, an EVM settle or session open used to sign and broadcast whatever verified, so an authorization from an unfunded wallet cost the canister a threshold signature, the RPC reads and gas, with the send lock held. The transfer is now simulated first (`eth_call`, 2‑of‑N, as the broadcast runs it) and signed only when the providers agree it succeeds. What the simulation cannot see is bounded: an authorization must have 120 s left; one inbound transfer per payer is in flight; a payer whose sent transfer reverts is refused for an hour (5 minutes when the authorization reads used: cancelled, or executed first by a copier), and one whose transfer is unconfirmed after the polls for 5 minutes; simulations take a budget token before their outcall (10 at once, one more every 6 s, given back only when the transfer goes out); and inbound work stops below 500B cycles. Remaining: one reverting broadcast per wallet per chain and token, per hour where the polls see it with the authorization unused and per 5 minutes otherwise; and anyone can spend the simulation budget (honest payments then wait up to a minute). See CHANGELOG 2.23.1, known residuals.
- **MCP server.** Well‑designed two‑tier (operator vs LLM) trust with default‑deny on dangerous tools — **but the reference demo invocation turns the safety off** (`IC402_MCP_ALLOW_DANGEROUS_TOOLS=1`, `IC402_MCP_ALLOW_SECURITY_CHANGES=1`, `autoPayment`). Do **not** copy the demo's environment into production; keep the safe defaults. Since 2.22.0 the canister, host and identity come only from the operator (`IC402_MCP_CANISTER_ID`, `IC402_MCP_HOST`, `ICP_IDENTITY_PEM` or the config file); `configure` and a per‑call `canisterId` can change them only with `IC402_MCP_ALLOW_SECURITY_CHANGES=1`, and local development needs `IC402_MCP_LOCAL_DEV=1`. A `confirm:true` call must repeat what the human approved — `fetch_x402` the proposed terms, `submit_request` the `amount`, `open_session` the `maxDeposit` — and is refused if the canister now asks something else; a `fetch_x402` failure after the paid request was sent is reported as possibly paid. Outbound fetches are SSRF‑guarded — every host is validated *and DNS‑resolved*, rejecting names that resolve to private/metadata IPs (DNS‑rebinding). **Residual:** the OS re‑resolves at connect time, so a host validated‑public can still rebind before the socket opens; full closure needs IP‑pinning at the transport (a custom undici dispatcher) — tracked as a follow‑up.
- **Upgrades.** The example is a persistent actor with **no migration function**; adding stable fields breaks in‑place upgrade, and the supported remedy is a *state‑dropping fresh deploy* that discards escrow/sessions/grants/nonces **and any funds parked mid‑settlement**. Drain and settle before upgrading. (Tracked as **B1** in [`production-readiness.md`](production-readiness.md).)
- **Dependencies / supply chain.** `@ic402/client`'s only runtime deps are `@icp-sdk/core`, `cborg`, and `viem`; `@ic402/mcp` adds the official `@modelcontextprotocol/sdk`. A `pnpm audit` / Socket scan flags a few **transitive** advisories — `ws` (via viem's **WebSocket** transport) and `hono`/`path-to-regexp`/`fast-uri` (via the MCP SDK's **HTTP/SSE** transports). ic402 uses **neither** transport: the EVM client uses `http()` RPC, and the MCP server is **stdio‑only** — so these are **not reachable** in ic402's usage, and the fixes are upstream. The `cborg` "shell access" flag is a test‑only file inside that library, not runtime. These are trusted, essential libraries doing expected things.

## 6. Shared EVM pool solvency (operators)

All three EVM subsystems — x402 charges, streaming sessions, and the service marketplace — settle from **one** tECDSA‑derived address. The library bounds *session* over‑allocation via `gate.setEvmPoolCap(cap)` (a per‑chain+token ceiling on outstanding session deposits; the example sets one), but it does **not** automatically reconcile the marketplace's `settleToOperator`/`refundOnRail` or the controller's `sweepEvm` against that ceiling. So the canister can pay marketplace/sweep funds out of the *same* balance that backs open session refunds.

What you must do as an operator:
- **Fund the EVM address at or above your `setEvmPoolCap` ceiling**, and treat the cap as a contract you keep solvent.
- **Don't `sweepEvm` funds that back open sessions** — `sweepEvm` sends an operator‑chosen amount with no record of what's owed; only sweep genuine surplus.
- **Monitor the on‑chain balance** against `health()` session counts; if you also run the marketplace on EVM, size its throughput so settle/refund outflows stay within the funded surplus.

This shared‑pool solvency is a **load‑bearing operator invariant**, not an automatic guarantee. A system‑wide on‑chain‑balance reservation (marketplace/sweep consulting `totalAllocated`) is a tracked follow‑up.
